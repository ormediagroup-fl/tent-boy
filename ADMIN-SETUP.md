# Tent Boy CMS: setup and daily use

## Current status

The dashboard is live at https://tent-boy-admin.orportraits.workers.dev/admin/. Owner GitHub sign-in, loading 12 products, authenticated preview, and saving an unchanged draft have been verified. Unauthenticated content and preview requests return 401. The public website remains unpublished. DNS and Squarespace settings remain unchanged. The following setup steps document the configured services and recovery procedure.

The code uses a small purpose-built Git-backed CMS instead of Decap. Decap's standard GitHub backend authenticates the editor in the browser and gives that browser a GitHub token. This dashboard instead uses a backend-for-frontend: GitHub tokens and the GitHub App private key stay on the Cloudflare Worker. The browser receives only a random, HttpOnly session cookie plus a CSRF value. There is no password, personal access token, or OAuth secret in public JavaScript.

## Architecture

- **Public website:** GitHub Pages at tentboy.orportraits.com.
- **Entry point:** `/admin` on the public site redirects to `https://YOUR-WORKER.workers.dev/admin/`. The address changes to the secure dashboard host. This is intentional: GitHub Pages cannot execute authentication code. It also avoids third-party cookies that iPhone Safari may block. No DNS change is needed for the dashboard's workers.dev address.
- **Dashboard / API / preview:** Cloudflare Worker + static assets, all on one origin.
- **Authentication:** GitHub OAuth authorization-code flow, PKCE, one-use state, and a fixed numeric GitHub account ID allowlist. GitHub handles your passkey / two-factor login. Sessions expire after eight hours; signing out removes the server session.
- **Repository access:** Separate GitHub App installed on **only the Tent Boy repository**, Contents read/write and Metadata read permissions. Installation tokens are short-lived and remain on the server. No access to OR Portraits is requested.
- **Session storage:** Cloudflare D1 stores only hashed session identifiers, CSRF values, account ID, expiry, and short-lived OAuth state / PKCE verifier. No customer database or photo storage service is needed.
- **Content storage:** `content/site.json`; uploaded images in `assets/uploads/`. These are ordinary Git files managed through forms.
- **Drafts:** `tentboy-cms-draft` branch. Save Draft commits content and uploaded photos atomically to this branch, without changing `main` or the public site.
- **Publishing:** After review, Publish advances `main` to the saved draft without force-pushing. A GitHub Actions build validates content, optimizes images, uploads `dist/`, and deploys GitHub Pages. A failed build leaves the prior successful deployment live.

## Required accounts / permissions

1. A GitHub account and a separate Tent Boy repository. Public repository Pages can use GitHub Free; Pages for private repositories requires a qualifying GitHub plan. A public source repository exposes draft history and original assets—Hide is visibility control, **not confidentiality**. Never upload private customer images or sensitive data.
2. A Cloudflare account with Workers and one D1 database. Hosting the dashboard on workers.dev does not require moving orportraits.com DNS to Cloudflare.
3. A GitHub OAuth App for sign-in (no repository scopes requested).
4. A GitHub App for narrowly scoped repository writes.
5. Owner approval before any external deployment, repository upload, enabling Pages, GitHub App installation, or DNS changes. The project contains only templates until those actions are authorized.

## One-time installation (technical setup)

Use this `website` folder as the **repository root**, not the parent PDF workspace. The `.github` directory must be included. Do not upload `dist`, `node_modules`, `.pnpm-store`, `.dev.vars`, keys, or the parent workspace. Keep the `.gitignore` provided.

Install Node.js 22 or later, then from the project root:

```sh
npm install --ignore-scripts
npm test
npm run build
```

Sharp uses packaged native binaries. If your installation platform cannot load Sharp, install the appropriate optional platform dependencies rather than disabling validation. A package lock generated by npm should be committed after the initial installation; subsequent deployments can switch to `npm ci`. This environment could not reach npm, so local builds were verified with the bundled Sharp 0.35.5 runtime matching the pinned dependency.

### A. Reserve the Worker name and create D1

After approval, install the official Cloudflare Wrangler CLI (`npm install --save-dev wrangler@4`) and authenticate with `npx wrangler login`. Run the following from `dashboard/`:

```sh
npx wrangler d1 create tent-boy-admin
```

Copy its database ID to `dashboard/wrangler.toml`. Establish the intended Worker URL from your Cloudflare account's workers.dev subdomain and the Worker name `tent-boy-admin`. Set `ADMIN_ORIGIN` to that exact HTTPS origin with **no trailing slash**. All settings containing REPLACE must be filled before deployment. Do not enable observability request-body logging or log cookies, authorization codes, credentials or tokens.

### B. Create the GitHub OAuth App (identity only)

In GitHub account Settings → Developer settings → OAuth Apps → New OAuth App:

- Name: Tent Boy Admin Login
- Homepage: the dashboard's HTTPS origin
- Authorization callback: `https://YOUR-WORKER.workers.dev/callback`

Set `OAUTH_CLIENT_ID` in wrangler.toml. Store the client secret through Wrangler's **interactive secret prompt**, never in a file or command argument:

```sh
npx wrangler secret put OAUTH_CLIENT_SECRET
```

The OAuth flow requests no repo scopes. It uses GitHub only to identify you. Set `ALLOWED_USER_ID` to your **numeric GitHub user ID**, obtained from the GitHub API `https://api.github.com/users/YOUR-USERNAME`. Account ID remains stable when you rename your account.

### C. Create and install the repository GitHub App

GitHub Settings → Developer settings → GitHub Apps → New GitHub App:

- Name: a unique Tent Boy content writer app name.
- Homepage: dashboard origin.
- Disable webhooks; no webhook endpoint is used.
- Repository permissions: **Contents: Read and write**; Metadata read is automatic. No Actions, Administration, Organization, or Account permissions are required.
- Installation: only your account; install on **Only select repositories → tent-boy**.

Copy App ID, installation ID (visible in the installation configuration URL), repository owner and repository name into wrangler.toml. Use a `main` default branch.

Generate a private key in GitHub. GitHub commonly supplies PKCS#1 PEM; the Worker expects **PKCS#8** (`BEGIN PRIVATE KEY`). Convert locally using OpenSSL if needed:

```sh
openssl pkcs8 -topk8 -nocrypt -in downloaded-github-app-key.pem -out tent-boy-app-key.pkcs8.pem
```

Keep both keys outside the repository and out of chat. Set the Worker secret via the interactive prompt, pasting the complete PKCS#8 PEM including headers:

```sh
npx wrangler secret put APP_PRIVATE_KEY
```

GitHub OAuth credentials identify the editor; GitHub App credentials write the repository. These are deliberately separate. Never grant the OAuth App repository scope.

### D. Initialize and deploy the dashboard

From dashboard/:

```sh
npx wrangler d1 execute tent-boy-admin --remote --file=schema.sql
```

From the project root run `npm run build` to prepare the shared preview and validation files. Then, only after deployment approval, from dashboard/:

```sh
npx wrangler deploy
```

The Worker URL must exactly match ADMIN_ORIGIN and the OAuth callback. Test authorized login, unauthorized-account rejection, save, logout, and session expiry before enabling public publishing. Use current official CLI releases and record the resolved dependency version in the lockfile.

### E. Enable GitHub Pages publishing

In the Tent Boy repository:

1. Set repository **Settings → Secrets and variables → Actions → Variables → ADMIN_ORIGIN** to the dashboard origin. This is a public URL, not a secret.
2. Enable GitHub Actions, then choose **Settings → Pages → Source: GitHub Actions**. This replaces the older branch-publishing instructions; do not deploy the source folder directly. The workflow is gated off until the repository variable `PUBLISH_ENABLED` is set to `true`. Set that variable only after website publishing approval, then run the workflow manually for the first deployment.
3. After approval, upload/push the project root to `main`. The included `.github/workflows/pages.yml` runs on `main` changes or manual dispatch. Draft saves do not deploy.
4. Follow the workflow to a successful deployment, and test the reported Pages URL. Confirm `/admin/` opens the secure dashboard. Relative paths support the default GitHub project URL too.
5. If the repository has branch rules requiring pull requests or signed commits, the App's direct fast-forward publication may be blocked. Do not weaken existing rules automatically; use a dedicated repository and explicitly decide the publishing rule, or adapt publication to a reviewed PR workflow before launch.

### F. Custom subdomain (separate approval)

1. Verify orportraits.com ownership through GitHub account Pages settings with the exact TXT record supplied by GitHub.
2. Add `tentboy.orportraits.com` in repository Settings → Pages → Custom domain.
3. At the existing DNS provider, add **only** `CNAME tentboy → YOUR-GITHUB-ACCOUNT.github.io` (no protocol or repository path). Check for conflicts first.
4. Wait for validation/certificate issuance, enable Enforce HTTPS, and test the website plus `/admin`.
5. Preserve all existing Squarespace root and www records. Verify orportraits.com and www.orportraits.com still serve the existing site.

No CNAME file or DNS record is created by the local build. GitHub Actions hosting uses the custom domain configured in repository Pages settings.

## Daily use from iPhone or computer

1. Visit `tentboy.orportraits.com/admin`, then Sign in with GitHub. Bookmark the dashboard on your iPhone if useful.
2. **Products:** Add a product, enter its name and optional description, choose a category, paste your actual Amazon affiliate URL, optionally upload a photo and add image description. Toggle Show and Featured. Use ↑ / ↓ to reorder; ordering is preserved within the selected category. Multiple products per category are supported. New products start hidden.
3. **Categories:** Add, rename, describe, reorder or delete. IDs are generated internally; changing the name preserves assignments. Move or delete products before deleting their category. Categories with no published products never appear in the public filters or catalog.
4. **Website:** Edit hero/headlines/intro, gear and setup copy, image, caption, note, badge, and strip text. Text is treated as text, not executable HTML.
5. **PDF guide:** Edit the description, actual price display, approved cover and Payhip URL. Turn Show off to hide the section and guide navigation. It cannot be shown without a valid Payhip URL. Price is display-only; update Payhip itself to change the checkout price.
6. **Social & disclosure:** Add TikTok or other HTTPS profile links. The exact required Amazon disclosure is fixed in code and always appears; the surrounding explanation is editable.
7. **Save draft.** The photos and edits go into Git history on the draft branch. They are not yet public website changes. Unsaved changes only live in this browser tab; save before closing.
8. **Preview.** This uses the public renderer with your draft data and selected photos. Choose Phone or Wide view. Save first and preview again to enable Publish.
9. **Publish saved draft.** Confirm the dashboard's publish prompt; this applies to your future dashboard operation after initial launch approval. The page reports submission, not deployment success. Use Check build progress; wait until GitHub Pages succeeds, then refresh the public website.

## Images and limits

- Upload JPEG, PNG or WebP from your device. iPhone HEIC support varies: export as JPEG if needed.
- Browser optimization strips metadata by redrawing images and converts to WebP, max 1600 px on the long edge, 82% quality, under 1 MB per upload. Photos above 20 MB or 40 megapixels are rejected.
- Builds validate decoding again with Sharp, apply orientation, resize without enlargement and re-encode only public referenced images. Original uploads remain versioned in Git; public pages receive optimized WebP images.
- Up to 500 products, 50 categories and 20 socials; save up to 20 new images at once and under the 8 MB request limit. Save in smaller batches when needed. Photos already saved need not be re-uploaded.
- No Amazon product images or prices are scraped. Use your own authorized product photos. Existing setup photos are not presented as photos of linked products. Products without photos show a clean text card.
- There is no separate media-library browser in this first version: upload/replace/remove images through the corresponding form. Removing a reference does not erase Git history. Periodic repository maintenance may be needed as original images accumulate.

## Recovery and maintenance

- Reload refuses to discard unsaved edits without confirmation. Concurrent drafts return a conflict instead of overwriting.
- If code on `main` changes while an older CMS draft exists, publishing is blocked. Record the intended draft changes, choose **Discard saved draft**, reload the current site, and reapply edits. Discard resets the draft branch to main; GitHub history can recover its former commit if necessary. Do not force-push main.
- If a build fails, inspect Actions. Fix the invalid content/image, save a new draft, preview, and publish again. The prior successful site remains live.
- Source changes to the renderer/styles require rebuilding and redeploying the Worker so its preview stays current. Content-only changes do not require redeploying the dashboard; draft image previews read through the authorized API.
- Uninstall the GitHub App to revoke repository writes; revoke OAuth App authorization to revoke sign-in credentials. Clear the D1 sessions table to force all sessions to sign out. Rotate Worker secrets if needed; never commit secrets.
- Keep Node, Sharp, Wrangler and workflow actions maintained. This is a small custom CMS, so future browser/API changes may require maintenance. It intentionally omits multi-editor permissions, scheduled posts, an approval queue, and customer data collection.

## Blog and visual editor

Open the dashboard → Blog → New post. Write a title, set a URL name, date and summary, and add a cover photo if desired. Use the visual toolbar for bold, italic, underline, headings, quotes, fonts, lists, links, undo/redo and inline photos. Fonts apply to the text block. Paste inserts plain text; apply formatting using the toolbar. Nested lists are flattened to one level.

New posts start hidden. Save draft, open Preview (Phone or Wide), then enable Include on public website, save and preview again, and Publish saved draft. Publishing submits the entire saved site draft and starts the existing GitHub Pages build. Posts are listed newest first by date; dates do not schedule publication. Hidden/deleted posts are removed on the next successful build. Changing a published URL breaks old links; keep URL names stable.

Drafts stay off the rendered public website, but this is a public GitHub repository: saved draft source and uploaded photos are readable in Git history. Do not save confidential information. Unsaved edits live only in the current tab. Image uploads support JPEG, PNG and WebP (export HEIC as JPEG), optimized to WebP up to 1600 pixels and 1 MB. Save at most 20 new photos at once. The existing 500 KB content-file limit still applies; split very large catalogs into separate files in a future upgrade if needed.

Published posts generate static HTML, page titles, descriptions, canonical/social metadata and sitemap entries. Rich text is stored as structured blocks, escaped on rendering and validated by the Worker and build. No raw authored HTML executes. No new accounts, subscriptions or services are required.
